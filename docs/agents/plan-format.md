# PLAN 格式规范

本仓库每轮修复的 PLAN 按此格式编写。骨架源自 `dev-expert` 的「任务拆解与执行」，此处固化为本项目的创建与验收基准；PLAN 的位置、命名与归档动作见 `AGENTS.md` 的「审查后的决策」。

完整实例：本地作业区 `.scratch/archive/` 下的任一份 plan 归档（该目录被 `.gitignore` 忽略，只在本地存在），如 `2026-09-18-plan-import-export-7a67b99.md`。

## 章节骨架

| 章节 | 内容 |
|---|---|
| `## 需求与授权` | 用户授权的原话与日期、起始基线 SHA、本轮已确认的范围与取舍 |
| `## 审查结论` | 本轮要修的问题清单（位置、严重度）与判定证据；审查产出直接落这里，不另建报告文件 |
| `## 影响面、依赖与护栏` | 涉及的模块与调用链、任务依赖顺序、并行分工、硬约束与禁止项 |
| `## Wave N：<主题>` | 每个 Wave 一组 `<task>`，见下节 |
| `## 回滚与检查点` | 回滚方式（代码 `git revert` 还是数据侧动作）、中断检查点的落点 |
| `## 状态` | 逐 Wave／任务标记 `[✔]`（已验证完成）或 `[ ]`（未完成） |
| `## 验收记录` | 实际跑过的命令与结果、证据类型、归档 blob 等可核对凭据 |
| `## 实施取舍与已知边界` | 与计划的偏差及原因、放弃的方案、生效条件（如需重启宿主） |
| `## 测试现场与清理限制` | 残留的临时目录与文件、被策略阻止的清理动作 |

前六项每轮必备；后三项按实际发生的情况保留或省略。

## 任务块

每个原子任务写成一个 `<task>`，六个子节点齐全：

```xml
<task type="auto">
  <name>T1：一句话任务名</name>
  <files>本任务读写或涉及的文件</files>
  <action>具体执行步骤，收敛到一个可验证的切片</action>
  <verify>验证方法与预期结果：命令、测试名、断言或检查清单</verify>
  <security>安全触发面的验证方法；不涉及则写“不涉及，原因：…”；禁止留空</security>
  <done>什么状态算完成</done>
</task>
```

- `type` 取 `auto`（代理可独立完成）、`human-verify`（需用户确认）或 `decision`（需用户拍板）。
- 任务编号 `T1`、`T2`… 跨 Wave 连续递增，供 `## 状态` 与交付说明引用。
- `<verify>` 指向可执行的东西：命令、测试名、断言。预期结果与实测结果分开写，后者落在 `## 验收记录`。
- `<security>` 指向具体风险：外部输入、权限、SQL、文件上传、路径越界、敏感信息泄露、长任务；本仓库还要覆盖 bridge 白名单、Host/Origin 校验与写盘边界。

## Wave 组织

- `## Wave N：<主题>` 是分组标题，主题一句话概括该组改动。
- 无依赖的任务同 Wave 并行；有依赖的进后续 Wave；可能改同一文件的任务同 Wave 内串行或合并为一个任务。
- 每个 Wave 在 `## 状态` 留一行标记；未完成写清阻塞原因，不因上下文耗尽而静默跳过。

## 验收标准

- 每个任务能在单个上下文窗口内完成，改动控制在 200 行代码量级。
- 优先垂直切片（端到端可验证的一小条），不按“全部模型 → 全部 API”的水平分层推进。
- 子代理产出经主线程复核后才计入完成度；「已返回结果」不等于「已验证完成」。
- 验证失败时记录失败原因与现场，不把未验证项写成已完成。
- 行为变化同步 README 或对应权威文档，作为该轮的验收项之一。
